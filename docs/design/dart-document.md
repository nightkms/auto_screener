# DART 공시 본문(원문) 수집·요약

## 왜 본문까지 받는가

auto_screener는 원래 공시를 **제목(`report_nm`)만** 보고 키워드로 분류했다.
문제는 제목만으로는 호재/악재가 드러나지 않는 공시가 많다는 것이다.

대표 패턴: 대주주 지분 변동 공시의 제목은 보통 `"주식등의 대량보유상황보고서(일반)"`
처럼 중립적이라 **증여·담보·승계 같은 핵심이 한 글자도 안 보인다.** 본문에 가서야
`"주식담보계약 및 주식증여계약 체결"`(승계 + 자금조달) 같은 사실이 나온다.
제목만 보면 막연히 악재로 기울거나 그냥 지나치게 된다.

→ 제목만으로 판단이 안 서는 유형은 **원문 본문을 받아 LLM으로 2~4문장 요약**해서
분석 컨텍스트에 주입한다.

## DART document API 디코딩 노하우

- 엔드포인트: `GET https://opendart.fss.or.kr/api/document.xml?crtfc_key=<KEY>&rcept_no=<접수번호>`
- 응답은 **ZIP**이다 (content-type이 `application/x-msdownload`로 와도 내용은 ZIP).
  안에 `{rcept_no}.xml` 파일 1개, 인코딩은 **UTF-8**.
- 마크업은 DART 전용 스키마(`dart4.xsd`): `TABLE/TR/TD/TE/TU/P …` 태그.
  태그를 제거하면 원본 50~110KB가 보통 **4~9천 자**로 줄어(약 90% 감소) LLM 요약
  입력으로 적합하다. 셀/행 경계(`</TR>`, `</TD>` 등)만 공백·개행으로 남기고 나머지
  태그는 지운다 → `data_loader._clean_dart_xml`.
- **핵심필드는 `ACODE` 속성으로 직접 추출**할 수 있다(요약 보조 + LLM 실패 시 fallback):

  | ACODE | 의미 |
  |---|---|
  | `RPT_RSP_NM` | 보고자 |
  | `SUM_CHN_RWN` | 보고사유 |
  | `CHN_RSM` | 변경사유 |
  | `CHN_RSN` | 변동사유 |
  | `TRD_RVL` | 계약상대방 |
  | `TRD_KND` | 계약종류 |
  | `TRD_RMK` | 계약비고 |

  정규식 `ACODE="<code>"[^>]*>([^<]*)<` 로 뽑는다 → `data_loader._extract_dart_fields`.

## 함께 잡은 버그: 공시 유형이 전부 "기타"로 박히던 문제

`list.json`(공시 **목록** API)은 **각 row에 `pblntf_ty`(공시 유형)를 주지 않는다.**
기존 코드가 `r.get("pblntf_ty")`를 읽다 보니 모든 공시 type이 `"기타"`로 떨어졌다.

해결: 목록을 받을 때 어느 카테고리 필터(`None`/`B`/`C`/`D`/`I`)로 조회했는지(루프
변수)로 유형을 판정한다. `None`(전체) 조회분은 일단 `"기타"`로 두고, 이후 B/C/D/I
조회에서 같은 `rcept_no`를 다시 만나면 정확한 유형으로 보강한다.
참고로 대량보유·소유상황보고서는 **D(지분)**.

## 어떤 공시의 본문을 받는가 (`should_fetch_document`)

본문 fetch + LLM 요약은 비용이 있으므로 대상을 좁힌다:

- 유형이 **지분(D)** 또는 **주요사항(B)** — 제목만으론 호재/악재가 안 드러나는 대표군
- `signal_level`이 **fatal/warn** — 맥락 확인 가치가 있음
- 위 유형 판정이 누락돼도 **제목 패턴**으로 한 번 더 거른다
  (대량보유·소유상황·특정증권·최대주주·증자·전환사채·합병·분할·감자·자기주식 등)
- **정기보고서(사업/분기, A)는 제외** — 실적은 `fnlttSinglAcnt`로 이미 구조화
  수신하므로 방대한 본문을 다시 받을 필요가 없다

종목당 본문 fetch+요약은 `MAX_DOCS_PER_STOCK`(기본 8)건으로 상한.
공시는 signal/최신 우선 정렬돼 있으므로 중요한 것부터 채워진다.

## 증분 수집 + 캐시 (매번 전체를 다시 받지 않기)

목록은 가볍지만 본문 fetch와 LLM 요약은 비싸다. 그래서 **목록은 증분으로 받고,
요약 결과는 캐시**한다.

- `data_loader.collect_disclosures_cached(ticker, name, corp)`
  - `metadata.last_disclosure_scan_date` **그 날부터** 다시 조회한다(하루 겹침).
    오전에 조회한 뒤 같은 날 오후에 올라온 공시를 놓치지 않기 위함. 첫 방문이면
    `since=None` → 180일 전체.
  - DART 신규분 + jsonl 캐시(과거 전체)를 `rcept_no`로 머지하고 180일 이내로 컷.
    → 매번 전체를 다시 받지 않아도 분석 컨텍스트에는 180일 공시가 다 들어간다.
  - 캐시에 있던 `summary`(본문 요약)는 머지에서 **보존**한다.
- `agents.enrich_disclosures(ticker, name, disclosures)`
  - 캐시에 `summary`가 있는 `rcept_no`는 **LLM 재호출 없이 재사용**.
  - 미캐시 + `should_fetch_document` 대상만 본문 fetch + `config.CLAUDE_SUB_MODEL`로 요약.
  - 새로 요약한 것만 jsonl에 append(`rcept_no`당 사실상 1회성).
  - `analyze_stock`이 **5개 서브에이전트 가동 전에** 호출 → 각 서브에이전트 프롬프트에
    "제목 + 본문요약"이 함께 들어간다(중복 fetch 방지).
- 캐시 위치: `analysis/by_ticker/<ticker>_<name>/dart_disclosures.jsonl`
  (각 row에 `summary` 필드).

## 요약 프롬프트 원칙

본문 요약은 분석 산출물 규칙을 그대로 따른다:

- 공시일 **시점의 사실만** 적는다. 추측·전망·매수/매도 의견 금지.
- 누가/무엇을/얼마나(주식수·금액·지분율)/왜(사유)를 **구체 수치로**.
- 증여·담보·계약 건은 **상대방과 목적**(승계·자금조달 등)을 드러낸다.
- 본문에 없는 내용은 지어내지 않는다.

## 정기보고서 '사업의 내용' 요약 (2026-10 추가)

공시 본문 요약은 정기보고서(A)를 제외하지만, **"누구에게 파는 회사인가"는 정기보고서에만 있다.**
재무 숫자·공시 제목만 받은 서브에이전트는 검색을 적게 하면 고객 집중 리스크에 닿지 못한다
(Sonnet 5.5 전환 후 에스앤디 사례: 매출 대부분이 단일 고객향인데 그 고객의 소스업체 인수 =
내재화 리스크가 보고서에서 사라졌다). 그래서 정기보고서는 **'II. 사업의 내용' 구간만** 따로 쓴다.

- `data_loader.latest_periodic_report(corp_code)` → 최근 400일 내 최신 사업/반기/분기보고서 메타.
- `data_loader.fetch_business_section(rcept_no)` → ZIP 안 본문 `{rcept_no}.xml`(감사보고서 등 첨부
  XML 제외)에서 `II. 사업의 내용` ~ `III. 재무에 관한 사항` 구간만 평문으로(최대 3만 자).
- `agents.enrich_business_overview(ctx)` → 주요 제품 비중·**매출처/고객 집중도**·원재료 매입처·
  생산능력/가동률·계약을 8~12줄로 요약. 고객명이 익명('A사')이면 익명 그대로 두고 매출채권 표로
  비중을 계산한다. 실명 확인은 서브에이전트의 WebSearch 몫(프롬프트 필수 조사 항목).
- 캐시: `analysis/by_ticker/<ticker>_<name>/business_overview.json` — `rcept_no`가 같으면 재사용,
  새 정기보고서가 나올 때(분기 1회)만 LLM 요약. 요약 실패 시 직전 캐시라도 쓴다.
- 컨텍스트에는 `## 사업 구조 (DART <보고서명> … rcept_no=…)` 블록으로 출처와 함께 들어간다.

관련: [이벤트 시간/시제 룰](event-time-rule.md), [출처 추적 원칙](source-tracking.md)

## 정기보고서 원문 다운로드 + 재무제표 본표 요약 (2026-11 추가)

`fnlttSinglAcnt`는 주요계정 몇 개(매출·영업이익·자산·부채 등)만 준다. 그래서 분기보고서가 나온 날에도
**분기 3개월 순이익·금융손익·중단영업·현금흐름이 컨텍스트에 없었다**. 2026-11-16 스피어 사례에서 원문 연결
손익계산서에는 3Q(3개월) 순손실 -145억·금융비용 220억, 누적 영업현금흐름 -1,009억이 있었다. 그런데 분석가들은
"3Q 순이익 미확인"이라고 썼다.

- `data_loader.download_periodic_report(rcept_no, ticker, name)` → 정기보고서 원문을 받아
  `analysis/by_ticker/<ticker>_<name>/dart_reports/<rcept_no>.pdf`(원본)·`.txt`(평문)로 저장한다. 접수번호는
  불변이라 `.txt`가 있으면 다시 받지 않는다. '사업의 내용'과 '재무' 구간이 같은 파일을 쓴다(보고서당 1회).
  - **1순위: DART 웹사이트 PDF**(뷰어의 '다운로드 → PDF'와 같은 경로). `dsaf001/main.do`에서 `dcm_no`를 얻고,
    다운로드 창 `pdf/download/main.do`를 먼저 열어 세션 쿠키를 받은 뒤 `pdf/download/pdf.do`를 부른다.
    쿠키 없이 부르면 200에 빈 본문이 온다. 텍스트는 `pypdf`로 추출한다. 표의 한 행이 한 줄로 유지돼 3개월·누적·
    전년동기 숫자가 그대로 읽힌다. 페이지 꼬리말 `전자공시시스템 dart.fss.or.kr Page N`은 지운다.
  - **2순위: OpenAPI `document.xml`**. **당일 접수분은 OpenAPI 원문이 늦게 올라온다**(`014 파일이 존재하지
    않습니다`). 2026-11-16 에스앤디 분기보고서는 웹엔 있었지만 OpenAPI는 저녁까지 014였다. 그래서 웹 PDF가 1순위다.
  - 웹 경로는 비공식이라 바뀔 수 있다. 실패하면 OpenAPI로 떨어지고, 둘 다 실패하면 직전 보고서 요약 캐시를 쓴다.
- `data_loader.fetch_financial_section` → `III. 재무에 관한 사항`(줄 머리 제목만. 본문 속 인용 문구는 제외)
  ~ `3. (연결)재무제표 주석` 직전까지 자르고, 별도 본표 `4. 재무제표` ~ `5. 재무제표 주석` 직전을 덧붙인다
  (연결 대상이 없는 회사는 '2. 연결재무제표 — 해당사항 없음'뿐이라 별도 본표가 있어야 한다). 범위는 요약재무정보와 재무상태표·포괄손익(3개월/누적)·
  자본변동·현금흐름 본표다. 주석은 방대해서 뺀다. 보통 1~2만 자다.
- `agents.enrich_financial_statements(ctx)` → Sonnet이 손익(3개월·누적·전년동기)·재무상태·현금흐름 표를
  백만원 단위로 만들고, **회계적 noise**(파생상품·CB 평가손익, 지분법, 중단영업, 법인세수익)와
  '3개월 vs 누적' 방향 차이를 구분한다. 캐시는 `report_financials.json`이다(rcept_no가 같으면 재사용).
- 컨텍스트에는 `## 최신 정기보고서 재무제표 (DART … rcept_no=…)` 블록과 DART 뷰어 출처 URL이 들어간다.
  API 표와 다르면 원문이 우선이라고 명시한다.
- 함께 고친 버그: `_fetch_financials_all`이 같은 해 안에서 1Q→반기→3Q 순으로 조회했다. 그래서 3Q가 나와도
  '최신 비율'(영업이익률·부채비율 등)이 1Q로 계산됐다. 이제 연간→3Q→반기→1Q 순으로 조회한다.

## 분기 실적 추이(QoQ) — 네이버 분기표 (2026-11-16 추가)

정기보고서 원문은 '당기 3개월'과 '전년 동기 3개월'만 줘서 **직전 분기 대비(QoQ)가 안 보인다**. 에스앤디 3Q는
매출·영업이익·순이익이 직전 분기보다 -12~-25%였지만 보고서는 YoY(+12.8%/+2.0%/+0.6%) 위주였다.

- `data_loader.fetch_naver_quarterly(ticker)` → 네이버 모바일 `api/stock/<code>/finance/quarter`. 3개월 단독(억원·%),
  실적 확정 컬럼만(컨센서스·미반영 '-' 제외). 신규 분기는 네이버 반영이 며칠 늦다 → 최신 분기는 정기보고서
  원문 '당기 3개월'로 이어 붙이라고 컨텍스트에 명시.
- 분석 컨텍스트 `## 분기 실적 추이` 블록 + `prompts/valuation.txt`가 YoY·QoQ를 둘 다 쓰게 한다.
  **QoQ는 계절성을 걸러 해석**: 전년 같은 구간(예: 작년 2Q→3Q) 흐름과 비교해 계절 패턴인지 실제 후퇴인지 판정.
- 보고서 Q&A(`report_chat`)도 같은 분기표 + `report_financials.json`을 컨텍스트로 받는다. Q&A의 WebFetch는
  `finance.naver.com`을 막기 때문에(Claude Code 쪽 제한) 서버가 모바일 API로 대신 받아 넣는다.
